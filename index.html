02 Chatbot 聊天入口

Chatbot 的中文是聊天机器人。它最直接的特点，是你用自然语言问，它用自然语言回应。自然语言就是我们平时说的中文、英文，不要求先把请求写成程序。

例如，你输入“把这一段改得礼貌一些”，它返回一段新文字。这就可以是一项完整的聊天任务。早期一些聊天机器人按预先写好的问答规则回应；今天很多产品会调用大语言模型。两种都可以有聊天界面。

看 Best Friday 的这个界面：你在输入框里提出需求，结果出现在对话里。这里体现的是 Chatbot 这一层交互。至于里面只是生成了一段回答，还是已经查过资料、调用过工具，要继续看它实际做了什么。

同样，Codex 和 CodeBuddy 也有聊天入口，但你可能让它们进一步修改文件。因此，“Chatbot”和“Agent”不是两个互相排斥的盒子。聊天可以成为 Agent 的入口；Agent 也可以被定时任务或某个事件启动，不一定每次都有人打字。

03 LLM 理解与生成内容的模型

LLM 是 Large Language Model，中文叫大语言模型。它根据交给它的文字和其他支持的输入，生成回答，也可以分析材料、提出步骤，或者提出下一步需要调用哪个工具。

这里的“模型”，可以先理解为一套通过训练获得能力的计算系统。它不是整个应用。就像同一部手机可以装很多应用，同一种模型也可以被不同应用使用；同一个应用也可能换用不同模型。

假设我们让一个学习助手“根据这段笔记，解释什么是 API”。模型负责组织解释。换成 Best Friday，让它根据提供的品牌资料写一份分析，模型负责理解材料和生成分析。任务领域变了，模型承担的角色相近。

但“写出一份分析”和“真的读取了某个账户里的数据”是两回事。模型如果没有获得那些数据，就不能因为说得很像，便当作已经查过。它能提出“我需要查日历”，也不等于日历已经被读取。

04 Prompt 与 System Prompt

刚才我们说“保留原功能，只修改标题和筛选”，这句话是在告诉助手这次工作的要求。给模型的任务说明、要求和相关输入，通常叫 Prompt，中文叫提示词。它可以是一整段说明，不只是一两个词。

假如我们自己开发一个网页修改助手，就可以预先规定：“先读已有项目；不确定时先澄清；没有实际修改和检查，不得宣称完成；公开发布前须由用户确认。”这类由应用预设的行为指令，就是这里要讲的 System Prompt，系统提示。它不是某个聊天产品隐藏提示词的原文，而是我们的教学设计。

系统提示可以回答六件事：第一，你承担什么角色；第二，你帮助谁完成什么目标；第三，应该执行哪些要求；第四，用什么语气、交付什么形式；第五，哪些事情有边界；第六，信息不足或失败时怎么处理。这六项来自 INT6137 第二周的系统提示设计。[13]

05 用户消息 助手消息与消息角色

User Prompt 是用户当前提出的要求，比如“把标题改成读书活动日历”。Assistant Message 是助手的消息，比如“我已找到标题所在的文件”。一条是请求，一条是回复，不能因为它们都是中文，就把作用看成一样。

Message Role 叫消息角色，用来标明消息来自哪一方。INT6137 第二周的例子用了 system、user、assistant，分别标明系统、用户和助手。[13] 这是消息的来源标签，不是把“老师”或“营销专家”写进标签里；具体职责要写在指令内容中。

在开场例子里，用户说“改标题”不表示已经改过；助手说“已经完成”也需要对照文件和检查结果。我们保存助手的旧回答，是为了理解对话经过，不是给旧回答盖上正确的章。

课件有时把模型回复称作“助手提示”。今天我们说“助手消息”，更容易记住它与系统指令的区别。一个系统也可以提供示范消息帮助模型理解格式，但示范内容和当前实际完成的工作仍要分开。

06 History 与 State

先回看我们刚才改过的标题。第一句是“我的学习日历”，后来改成“读书活动日历”。History，历史对话，记录这两句话发生过；State，当前任务状态，记录现在应该采用哪一个标题。

历史像按时间保存的谈话记录；状态是此刻任务的有效条件。这里可以记下：当前标题为读书活动日历；筛选范围为学习类事件；电脑和手机都要支持；原有功能要保留；目前等待检查。它们服务于下一步工作，而不是重复整段聊天。[14]

如果只保存历史而不处理更正，两种标题可能同时出现在材料里，系统还要判断哪个有效。如果只留一个最新标题却完全丢掉历史，又可能解释不了为什么改名。两种信息各有用途。

换到 Best Friday：历史里有“预算300元”和“改成500元”；当前状态采用500元，仍保留“先交草案，不发布”。不能把它们相加成800元，也不能把改预算理解成获得发布授权。

07 Session 与 Memory

假设你同时打开两个任务：一个改读书活动日历，一个改个人主页。你说“标题改一下”，应用首先要知道这句话属于哪一边。Session 是会话，Session ID 或 Chat ID 是用于识别这场会话的标识。它帮助应用找到相应记录，本身不包含整段记忆。[14]

找到会话以后，应用可以取回历史和当前状态。它们可以保存在当前运行过程、应用存储或其他数据服务中，具体产品有不同安排。换了对话窗口、设备或账号以后能否继续，不能只凭一个聊天框判断。

Memory 中文叫记忆，在这里指把信息留下，并在合适的时候重新取用。当前任务的状态可以在短期内复用；如果用户明确希望以后都先检查手机效果，这个偏好也可能跨任务保存。是否保存、保存多久、下次是否相关，都要由应用管理。

10 API 与系统提示的关系

API 的英文全称是 Application Programming Interface，中文是应用程序编程接口。先不用背这个长名字。你可以把它理解为：一个程序公开一套别人可以怎样请求它、需要提供什么、会返回什么的约定。其实就是大家入境香港时填的那个表。

人可以打开天气网站，在搜索框里输入香港。程序之间也需要一个可以请求天气的入口：告诉它地点和日期，它返回相应的数据。这套入口和规则就是 API 的一种体现。

它通常要说明三件事：可以做什么，需要给什么信息，结果以什么形式返回。

比如查询日程要给日期范围，创建日程可能还要给标题和开始时间。缺了必要信息，请求可能失败；没有权限，也可能被拒绝。

Best Friday 联系外部模型服务，可以使用模型 API。一个旅行助手查天气，可以使用天气 API；办公助手读取在线日历，可以使用日历 API。它们都是接口，但所提供的能力不同。

13 Tool 与 Function

API 像对方公开的办事规则，Connector 像我们这边已经准备好的办事通道。这个类比只帮助分清角色：连接器依然是软件，不是一位真人，也不能绕过对方的权限。

16 MCP 共同的能力接入规则

MCP 的全称是 Model Context Protocol，中文是模型上下文协议。Protocol 就是协议：参与通信的程序共同遵守的一套约定。它规定怎么介绍可用能力、怎么发出请求、怎么把结果交回来。

为什么要有这件事？如果每个外部工具都用完全不同的方式介绍自己，每个 Agent 应用就要分别适配。MCP 提供一种共同语言，让支持它的应用和服务可以按共同规则交流。它减少重复接线的工作，但不保证任意两个产品插上就拥有所有能力。

我们先认识三个位置。Host 是你正在使用的 AI 应用；Client 是这个应用里负责保持某条 MCP 连接的部件；Server 是向它提供能力的程序。“Server”这里说的是提供服务的角色，它可以在你电脑上，也可以在远处运行，不一定是一台很大的机器。[5]

Workflow 中文叫工作流，就是一件事情的步骤和衔接关系。例如准备活动通知，可以先读活动信息，再起草，再由负责人检查，最后发布。前一步的产物，会成为后一步要用的东西。

流程可以很固定，也可以包含分支。比如“信息不完整就先补问”，或者“日期冲突就换时间”。有工作流不等于一定有 Agent：普通表单提交后自动发通知，也可以是预先写好的流程。

Best Friday 中，一类任务可以按读取相关资料、形成方案、等待确认、执行或保存的步骤组织。这里不需要大家懂广告业务；换成学校活动安排，也是“取得信息—形成草案—检查—确认”的关系。

Skill 与 Workflow 也有区别。Skill 可以用文字指导一个工作流；Workflow 则强调实际要经过哪些步骤、分支和等待点。方法说明里写了“先检查”，不等于应用已经强制设置了检查关口。

现在我们知道了流程长什么样。但任务运行到一半，究竟应该进入哪一步，谁来协调？这就引出编排层。

20 Orchestration Layer 编排层

Orchestration Layer 中文叫编排层。Orchestration 原本有组织配合的意思；放在 Agent 系统里，就是协调模型、工具、数据和各个步骤，让它们围绕当前目标配合。

例如，一个活动助手先查日期，再查教室。如果两边结果冲突，它不能把两个互相矛盾的结果直接贴给用户，就说任务完成。系统需要决定继续查询、修改方案，还是向人补问；已经得到的结果也要送到下一步需要的位置。

这些安排有的由固定程序规定，有的交给模型判断，也可以两者结合。编排层不是必须另买一个软件，也不一定是另外一个更聪明的模型。我们把它单独讲，是为了认出“协调工作”这份职责。

21 Harness 运行支撑

Harness 这个英文原来有套具的意思。在 Agent 开发里，常用它指模型外面那套运行支撑：把指令和上下文交给模型，接住工具请求，安排执行，带回结果，继续下一轮，并管理运行状态和限制。Anthropic 对自家系统的说明，也把反复调用模型、分派工具请求的循环作为 Harness 的核心职责。[12]

把刚才的任务想成一段正在进行的工作。工具十秒没返回怎么办？已经试了很多次还没成功怎么办？用户按下停止怎么办？中间失败以后，还记不记得哪些步骤做过？这些不是靠模型再说一句“我会继续”就解决的。

Best Friday 的执行内核有对模型调用、工具执行和状态的管理，这是我们在项目里观察到的运行支撑。对一个代码 Agent，同类职责可以表现为管理工作文件、运行命令、接收错误，再继续修改；对办公 Agent，则可能表现为等待确认和保存任务进度。

22 权限 人工确认与结果检查

权限就是系统允许谁对哪些对象做哪些操作。读一份文档、修改这份文档、把它发给别人，是不同权限。连上一个服务，也不代表里面的所有操作都可以做。

人工确认是把某些决定交还给人。比如助手可以先拟好一封邮件，展示收件人和正文，等你确认后再发送。确认不能只是一个模糊的“继续”，最好让人知道这次具体要发生什么。

结果检查则发生在行动以后：文件有没有真的改好？日历里是不是出现了那条事件？返回的是成功结果，还是一个错误？“模型说成功”“工具报告成功”和“实际结果符合要求”，是需要对照的几份证据。

在 Best Friday 的模拟操作里，可以观察提案、确认和执行结果的区别；因为是模拟环境，不能把成功提示当成真实平台已改变。GitHub Copilot 的代码任务可以把修改交给人审阅，这又是另一个行业里保留人工判断的位置。[1]

23 分工 分流 日志与评估

任务复杂以后，应用可以把资料查找和结果检查分给不同助手角色。这叫 Subagent，子 Agent；多个这样的角色配合，就是多 Agent 协作。对今天的小日历任务，一个助手也可以完成，多个角色不是必需配置。

Routing 叫路由或分流，是按任务选择模型、工具或工作路径。例如需要读文件时走读取工具，需要补充日期时问用户。它是组织工作的一个动作，不是另一个神秘的大脑。

日志记录实际发生过什么，比如读过哪个文件、工具返回了什么错误。评估则拿任务标准来检查：新标题有没有生效、筛选是否在两种视图都工作。日志很长，不代表结果正确；只看最后一句“完成”，又可能看不到失败。

Best Friday 的宣传草案也可以分开检查资料依据和预算，但这属于可选工作安排，不能仅凭我们画了两个角色就认定产品已有多 Agent 实现。我们需要分清已经观察到的能力与教学上可以采用的设计。

24 Agent 围绕目标推进任务的系统

Agent 常译作智能体。在今天这节课讨论的现代大模型 Agent 中，关键是：系统围绕目标，让模型参与选择下一步，使用可用工具采取行动，再根据真实结果决定继续、调整、向人求助或结束。

Best Friday 是一个围绕特定工作领域设计的案例；Codex、CodeBuddy 和 GitHub Copilot 是代码工作中的例子；使用 Copilot Studio 构建的 Agent 可以面向办公或业务系统。大家要看它们怎样完成目标，而不只看产品页面写了哪个名词。

第三轮 看清楚 保存到哪里

现在我们在页面里添加一条虚构事件，比如“示例读书会”，然后刷新。事件还在，说明本浏览器的草稿保存生效了。它用的是 localStorage，可以先理解为浏览器给这个网站保留的一小块本地存储空间。

这时请特别注意：它还在你的当前浏览器里，不等于已经出现在另一个设备上。电脑和手机可以读取同一份已经发布的 events.json，但你刚添加的本机草稿不会自动上传。[10]

点击导出，会得到一个包含共享日程与本机草稿的数据文件。维护者检查后更新项目里的events.json，再完成发布，其他设备刷新才会读到更新。已发布的草稿还留在本机时，要按项目说明清理，避免重复显示。

到这里，大家也能看出普通网页和 Agent 的区别：网页按既定程序保存、显示日程；CodeBuddy 则围绕你不断补充的目标，读取和修改这个程序。两者在同一次课堂里出现，承担的角色完全不同。
